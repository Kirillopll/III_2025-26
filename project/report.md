# Отчёт по проекту "Сервис оценки кредитного риска"

## 1. Постановка задачи

Цель проекта - построить сервис кредитного риск-скоринга.
Сервис получает признаки клиента и заявки на кредит, после чего оценивает вероятность дефолта.

Пользователь сервиса - кредитный аналитик или внутренний банковский сервис, которому нужен быстрый ML-скоринг заявки.

Тип задачи - бинарная классификация:

- `TARGET = 0` - клиент не допустил дефолт;
- `TARGET = 1` - клиент допустил дефолт.

Практический результат - REST API, которое возвращает:

- вероятность дефолта;
- категорию риска `low`, `medium` или `high`.

## 2. Данные

Используется открытый датасет Kaggle Home Credit Default Risk.

В текущей версии используется основной файл:

```text
data/raw/application_train.csv
```

Дополнительные файлы датасета (`bureau.csv`, `previous_application.csv`, `installments_payments.csv` и другие) загружены в `data/raw/`, но пока не используются, чтобы не усложнять первую рабочую версию.

Для первичной проверки данных добавлен скрипт:

```bash
python scripts/inspect_data.py
```

Он сохраняет краткий профиль в:

```text
artifacts/data_profile.json
```

## 3. Подготовка данных

В пайплайне обучения выполняется:

- удаление ID-колонки `SK_ID_CURR` из признаков;
- разделение на train/validation через stratified split;
- обработка числовых признаков:
  - заполнение пропусков медианой;
  - масштабирование через `StandardScaler`;
- обработка категориальных признаков:
  - заполнение самым частым значением;
  - one-hot encoding.

Обработка признаков включена в единый `sklearn Pipeline`, поэтому те же шаги применяются и при обучении, и при работе API.

## 4. Модели

Реализованы три модели:

- `DummyClassifier` - простейшая базовая модель;
- `LogisticRegression` - интерпретируемая классическая модель;
- `RandomForestClassifier` - нелинейный ансамбль на деревьях.

Список моделей и параметры задаются в:

```text
configs/model.yaml
```

## 5. Метрики и выбор модели

Используются метрики:

- `ROC-AUC`;
- `Average Precision`;
- `Precision`;
- `Recall`;
- `F1`.

Главная метрика выбора - `Average Precision`, потому что задача дефолта обычно имеет сильный дисбаланс классов: дефолтов заметно меньше, чем обычных заявок.

После обучения сохраняются:

```text
artifacts/credit_risk_model.joblib
artifacts/credit_risk_model.metrics.json
```

Результаты проверочного запуска на `20000` строках `application_train.csv`:

| Модель | ROC-AUC | Average Precision | Precision | Recall | F1 |
| --- | ---: | ---: | ---: | ---: | ---: |
| DummyClassifier | 0.500 | 0.079 | 0.000 | 0.000 | 0.000 |
| LogisticRegression | 0.730 | 0.191 | 0.151 | 0.639 | 0.245 |
| RandomForestClassifier | 0.704 | 0.178 | 0.178 | 0.354 | 0.237 |

Лучшей моделью по `Average Precision` стала логистическая регрессия (`LogisticRegression`).
Она выбрана для API-сервиса, потому что дала лучший баланс качества и простоты.

## 6. Сервис

Сервис реализован на FastAPI.

Эндпоинты:

- `GET /health` - показывает, загружена ли модель;
- `POST /predict` - возвращает вероятность дефолта и категорию риска;
- `GET /model-info` - возвращает название модели, дату обучения, метрики и число признаков;
- `GET /metrics` - отдаёт Prometheus-метрики.

Категории риска:

- `low` - вероятность меньше `0.10`;
- `medium` - вероятность от `0.10` до `0.25`;
- `high` - вероятность `0.25` и выше.

Пороги можно менять через переменные окружения или `configs/model.yaml`.

## 7. Наблюдаемость

Добавлены базовые элементы наблюдаемости:

- логи старта и ошибок предсказания;

- гистограмма задержки предсказаний `credit_risk_prediction_seconds`;

Добавлены pytest-тесты:

Запуск:

```bash

```

## 9. Безопасность и воспроизводимость

- Большие CSV-файлы не коммитятся.
- Модельные артефакты не коммитятся.
- Секреты не хранятся в репозитории.
- Пример переменных окружения лежит в `configs/.env.example`.
- Все основные параметры вынесены в `configs/model.yaml`.
- Есть Dockerfile и `docker-compose.yml`.

## 10. Ограничения и дальнейшая работа

Текущая версия намеренно простая:

- не используются дополнительные таблицы Kaggle;
- нет сложного feature engineering;
- нет MLflow;
- нет отдельного frontend-интерфейса.

Возможные улучшения:

- добавить агрегированные признаки из дополнительных таблиц;
- добавить CatBoost или LightGBM;
- сделать EDA-ноутбук с графиками;
- добавить объяснимость через feature importance или SHAP;
- подключить MLflow для трекинга экспериментов.
