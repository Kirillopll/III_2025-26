# Отчёт по проекту «Сервис оценки кредитного риска»

## 1. Постановка задачи

Цель проекта - разработать end-to-end ML-сервис, который оценивает вероятность дефолта клиента по признакам кредитной заявки.

Пользователь сервиса - кредитный аналитик или внутренний банковский сервис, которому нужен быстрый предварительный скоринг заявки.

Задача является бинарной классификацией:

- `TARGET = 0` - клиент не допустил дефолт;
- `TARGET = 1` - клиент допустил дефолт.

Результат проекта - REST API и простая HTML-страница, которые принимают признаки заявки и возвращают риск невозврата кредита и категорию риска: `low`, `medium` или `high`.

---

## 2. Данные

Используется открытый датасет Kaggle Home Credit Default Risk.

Основной файл текущей версии:

```text
data/raw/application_train.csv
```

В датасете одна строка соответствует одной кредитной заявке. Целевая переменная `TARGET` показывает, был ли дефолт.

В `data/raw/` также можно хранить дополнительные таблицы Kaggle: `bureau.csv`, `bureau_balance.csv`, `previous_application.csv`, `installments_payments.csv`, `credit_card_balance.csv`, `POS_CASH_balance.csv`, `application_test.csv`.

В текущей версии проекта они не используются, чтобы сохранить проект простым и воспроизводимым. Их можно подключить позже через агрегации по `SK_ID_CURR`.

## 3. Первичный анализ данных

По проверочному анализу `application_train.csv`:

- число колонок: `122`;
- доля дефолтов: около `8%`;
- числовых колонок: `106`;
- категориальных колонок: `16`.

Это подтверждает, что задача несбалансирована: дефолтных клиентов намного меньше, чем недефолтных.

```text
data/sample_application.csv
```

Она создаётся во время обучения командой:

```bash
python -m src.train
```

## 4. Признаки и подготовка данных

Список признаков зафиксирован в:

```text
configs/config.yaml
```

Числовые признаки:

- `CNT_CHILDREN`;
- `AMT_INCOME_TOTAL`;
- `AMT_CREDIT`;
- `AMT_ANNUITY`;
- `DAYS_BIRTH`;
- `DAYS_EMPLOYED`;
- `HOUR_APPR_PROCESS_START`;
- `EXT_SOURCE_2`;
- `EXT_SOURCE_3`.

Категориальные признаки:

- `NAME_CONTRACT_TYPE`;
- `CODE_GENDER`;
- `FLAG_OWN_CAR`;
- `NAME_INCOME_TYPE`;
- `NAME_EDUCATION_TYPE`;
- `NAME_FAMILY_STATUS`;
- `NAME_HOUSING_TYPE`;
- `WEEKDAY_APPR_PROCESS_START`;
- `ORGANIZATION_TYPE`.

Подготовка данных выполняется внутри `sklearn Pipeline`:

- числовые признаки: заполнение пропусков медианой и масштабирование;
- категориальные признаки: заполнение самым частым значением и one-hot encoding;
- целевая переменная не используется как признак.

Такой подход важен, потому что одинаковая обработка применяется и при обучении, и при работе API.

В пользовательской HTML-форме оставлены только понятные поля заявки: доход, сумма кредита, ежемесячный платёж, дата рождения, дата начала работы, количество детей и несколько категориальных признаков. Технические признаки датасета `EXT_SOURCE_2`, `EXT_SOURCE_3` и `HOUR_APPR_PROCESS_START` в интерфейсе не показываются, но передаются в модель как демонстрационные значения по умолчанию.

## 5. Модели

В проекте сравниваются:

- `DummyClassifier` - базовая модель;
- `LogisticRegression` - интерпретируемая классическая модель;
- `RandomForestClassifier` - нелинейная ансамблевая модель.

Основная метрика выбора - `Average Precision`, потому что классы в задаче дефолта несбалансированы.

Дополнительно считаются:

- `ROC-AUC`;
- `Accuracy`;
- `Precision`;
- `Recall`;
- `F1`.

## 8. API-сервис

Сервис реализован на FastAPI в модуле:

```text
src/service/app.py
```

Основные endpoints:

- `GET /` - пользовательская HTML-форма;
- `GET /health` - проверка состояния сервиса;
- `GET /metrics` - базовые счётчики запросов, ошибок и времени ответа;
- `GET /model-info` - информация о модели и метриках;
- `POST /predict` - оценка одной заявки;
- `POST /predict-batch` - пакетная оценка заявок;
- `GET /docs` - Swagger UI.

Запуск:

```bash
python -m src.service
```

## 12. Ограничения и дальнейшая работа

Текущая версия намеренно сделана простой:

- используется только `application_train.csv`;
- дополнительные таблицы Kaggle пока не агрегируются;
- нет глубокого подбора гиперпараметров;
- нет MLflow-трекинга;
- нет полноценного мониторинга качества модели после запуска.

Возможные улучшения:

- добавить признаки из `bureau.csv` и `previous_application.csv`;
- добавить CatBoost или LightGBM;
- расширить EDA-графики в notebooks;
- добавить SHAP или feature importance;
- подключить MLflow.
